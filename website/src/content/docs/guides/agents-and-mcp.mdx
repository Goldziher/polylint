polylint ships its own agent integration rather than expecting one to be bolted on: plugins for Claude
Code, Codex, OpenCode, Pi, Hermes and more, and a stdio MCP server exposing the same lint, format, cache, rules and config surface as
the CLI — with structured output an agent can consume directly instead of parsing terminal text.

## The operating rule

<Aside type="tip" title="poly first">
    polylint is one binary, `poly`, for both linting and formatting across every language in the
    repository. Prefer `poly lint` and `poly fmt` over invoking ruff, oxlint, biome, `rustfmt` or
    `gofmt` directly: poly runs them behind a single `poly.toml`, one report format, and one
    exit-code contract (ruff, oxc and biome as engines, `rustfmt` and `gofmt` as host subprocesses
    when installed). Over MCP, call the tools rather than shelling out.
</Aside>

<Aside type="caution" title="A first run may download">
    In a core build, a lint or format call may install engine components first. Check the result's
    `components` block: a needed component listed in `components.missing` was not available, so
    the files it would have handled were not checked. Gate on `summary.checked` and `isError`, not
    on an empty `results`.
</Aside>

## The plugin

```text
/plugin marketplace add polylint/polylint
/plugin install poly@poly
```

That registers `poly mcp` as a stdio server, plus **5 skills** and **2 slash commands**
(`/poly-check`, `/poly-fix`) that teach an agent poly's tiered backend model and when to reach for
lint versus format versus hooks.

For Codex, the same repository is the marketplace:

```sh
codex plugin marketplace add polylint/polylint
codex plugin add poly@poly
```

The plugin assumes `poly` is already on `PATH` — it does not bundle the binary — and its version
tracks the binary version in lock-step.

### OpenCode and Pi

Both install `@polylint/opencode-poly` from npm, which CI publishes with every release:

```sh
opencode plugin add @polylint/opencode-poly
pi install npm:@polylint/opencode-poly
```

The package contains 5 skills and the `/poly-check` and `/poly-fix` prompts. Pi runs `poly`
through its shell tool; it does not register an MCP server. Pi can also install straight from
Git — `pi install git:github.com/polylint/polylint`, or `pi install -l …` to save it in the current
project's configuration.

### Hermes

Install `poly-hermes-plugin` from PyPI into the Python environment Hermes runs in, then enable
`poly` under `plugins.enabled` in that installation's `config.yaml`:

```sh
uv pip install --python /path/to/hermes/venv/bin/python poly-hermes-plugin
```

Hermes gets one `poly_call` tool that bridges all four MCP tools (`list_tools` shows their
schemas), and the skills load by namespace, e.g. `poly:poly-mcp`.

### Other runtimes

Cursor, Gemini, Kimi, Factory and Copilot bundles are generated alongside these and attached to
every GitHub release as `poly-plugins-v<version>.tar.gz`; the
[plugin README](https://github.com/polylint/polylint/blob/main/plugin/README.md) lists each entry
point. The skills alone also install with `npx skills add polylint/polylint --skill <name>`.

## As a plain MCP server

Any MCP-capable client can run poly directly:

```json title="mcp.json"
{
  "mcpServers": {
    "poly": { "command": "poly", "args": ["mcp"] }
  }
}
```

`poly mcp --config <PATH>` pins a fallback config file for requests that do not name one.

The server honours a repository's config keys that run programs (tool `bin`, `env` and argv,
`[hooks]` whole-project jobs) only when the repository is [trusted](/polylint/guides/trust/) with
`poly trust`; `--trust` and `POLY_TRUST` do not apply to it, so a client cannot widen what a model
can make it run. It re-reads the trust store when it changes, so `poly trust` run in a terminal takes
effect on the server's next call, with no restart.

The Linux musl release binary links the server in. The other release binaries are core builds and
serve MCP through the downloadable `mcp` component instead: `poly mcp` installs it on
first use (unless `--offline` or `[components] install = "never"` forbids it) and hands it stdio, and
the component does its work through services the `poly` binary provides, so that binary carries no
async runtime.

## The four tools

The tools are split along the annotation boundary (ADR 0076): clients grant permissions per tool
name, so read-only and mutating operations are separate tools, and everything within one class is one
tool with parameters. Each returns typed `structured_content` plus one text block mirroring the CLI's
`--format json` — or the compact TOON encoding when asked for it. Tools declare no `outputSchema`;
the output schemas are MCP resources under `poly://schema/` (`lint`, `format`, `failure`,
`workspace`, `info/version`, `info/rules`, `info/components`, `info/cache`, `info/validate`,
`manage/cache`, `manage/components`, `identity`, `poly.toml`).

| Tool | Does | Annotations |
| --- | --- | --- |
| `check` | Lint or check formatting; writes nothing. | Not read-only, not destructive, idempotent, open-world |
| `fix` | Apply lint autofixes or formatting in place. | Destructive, open-world |
| `info` | Read-only introspection: version, config, validate, rules, components, cache. | Read-only, idempotent, closed-world |
| `manage` | Cache and component maintenance. | Destructive, open-world |

<Aside type="caution" title="`check` is not read-only">
    It runs the tools and hooks the repository's own `poly.toml` configures (`[tools.*]` `bin`,
    `args`, `env`), so a cloned repository can make it execute its programs, and it may download an
    engine component. It is therefore not annotated read-only, and a client should not auto-approve
    it for repositories it does not trust.
</Aside>

<Aside type="note" title="Upgrading from the fourteen-tool surface">
    The old names — `lint`, `lint_fix`, `format_check`, `format_write`, `workspace_lint`,
    `workspace_lint_fix`, `cache_stats`, `cache_clean`, `rules`, `config_show`, `components`,
    `components_install`, `components_uninstall`, `version` — are removed, with no aliases. Update
    client permission allowlists (for example `mcp__poly__lint` becomes `mcp__poly__check`) and any
    saved prompts.
</Aside>

### `check` and `fix`

`check` mirrors `poly lint` / `poly fmt`; `fix` mirrors `poly lint --fix` / `poly fmt --fix`, and
runs the whole-project phase in fix mode. Both take the same parameters:

- `kind` — `lint` (the default) or `format`.
- `scope` — `files` (the default) runs the per-file tier over `paths`, like `poly lint --workspace
  never` or `poly fmt`. `workspace` runs only the whole-project phase (`cargo clippy` / `cargo-sort` /
  `cargo-machete` / `cargo-deny` and configured inline whole-project jobs) over the whole repository;
  it is lint only and takes only `config`, `jobs` and `no_cache`. `all` runs both; lint only.
  **`scope: all` is what plain `poly lint` runs.** The default is `files` because the whole-project
  phase executes the repository's tools and can take minutes.
- `paths` (files or directories; empty means the current directory), `exclude` (gitignore-style globs
  merged with `[discovery] exclude`; unanchored globs match at any depth), `config` (path to a
  `poly.toml`), `include_excluded`, `only` / `skip` (mutually exclusive engine selection),
  `max_skips` (`0` is `--deny-skips`), `install` (`config` by default, `auto` or `never`),
  `on_missing` (`fail` or `skip`), `no_cache`, `jobs`, `debug`, and on `fix` only `fix_generated`.
- `format` — `json` (the default) or `toon`. It selects only the paired **text** block;
  `structured_content` is always JSON.

The result is the CLI's `--format json` document — `results`, `errors`, `skipped`, `summary`,
`configs`, and optionally `suppressed`, `components`, `degraded` and `discovery` — plus a `poly` identity
block.
`scope: workspace` returns the whole-project report (`passed`, `fixed`, `tools[]`); a failing tool is
a finding (`passed: false`), not an error. When the phase did not run, the result is an `isError`
failure instead: `untrusted` (the repository's `[hooks]` are not trusted) or `no_workspace_tools`
(nothing is configured, or the phase is disabled). `scope: all` returns the lint document with the
report under a `workspace` key, and sets `isError` when the repository is untrusted.

Arguments a tool cannot act on fail with a `usage` error naming the key, on all four tools: an unknown
key (`path` for `paths`), an invalid value, arguments that do not go together (`kind: format` with
`scope: workspace`), and a parameter that does not apply to the chosen `scope`, `action` or `topics`
(`exclude` with `scope: workspace`, `dry_run` with `cache_clean`).

<Aside type="caution" title="Whole-project scopes execute tools against the live worktree">
    A `workspace` or `all` scope applies no fixes under `check`, but it *executes* those tools
    against the live worktree, and their own side effects — a refreshed lock file, a populated build
    or type-checker cache — are not poly's to control.
</Aside>

### `info`

Read-only: it never downloads, never fetches, never writes (the `cache` topic does not create the
cache it measures) and never runs repository tools. `topics` is an array of `version`,
`config`, `validate`, `rules`, `components` and `cache` (default `["version"]`); the result has one key
per topic.

| Topic | Mirrors | Returns |
| --- | --- | --- |
| `version` | `poly --version` | Binary health: `executable_current`, `executable_status`, `uptime_seconds`, the full engine→version map (host-toolchain backends excluded) and `components`. |
| `config` | `poly config show --format json` | `{config, resolution}`: the merged effective configuration. |
| `validate` | `poly config validate` | `{valid, files: [{path, problems: [{path, key?, message}]}], partial: [{component, engines}]}`. |
| `rules` | `poly rules list --format json` | Every ast-grep rule a run would apply. With `test: true`, also runs the `*-test.yml` snippets; a failing test sets `isError`. |
| `components` | `poly components status` | The downloadable engine components and where each stands; with `paths`, which ones they need, which are missing and which a run would download. |
| `cache` | `poly cache stats --format json` | `{format_version, on_disk_version, namespaces[], total_entries, total_bytes}`. |

Besides `topics`, `info` takes `config`, `paths` (for `components`, the paths to judge; for
`validate`, config files or directories), `install` (the policy `would_download` assumes), `dirs` and
`test` (for `rules`) and `format`.

`info {topics: ["version"]}` still answers when the server's executable was replaced or deleted;
every other call fails until the server restarts. The `rules` topic never downloads: a core build
without the `astgrep` component reports it as missing. A topic the host cannot answer carries
`{error: {kind, message}}` under its key and sets `isError`.

Remote git `extends` bases are resolved from the local source cache at the `poly.lock`-pinned
revision and never fetched, by every tool, so the server stays network-free for config. A base that is
not cached is a `config` error telling you to run `poly lock` or a CLI `poly lint` once. `poly.lock` is
read on each call, so a `poly lock` run beside the server takes effect on the next one.

### `manage`

`action` selects the operation:

| Action | Mirrors | Parameters |
| --- | --- | --- |
| `cache_clean` | `poly cache clean` | |
| `cache_gc` | `poly cache gc` | `max_age_days`, `max_size` (for example `500M`, `2G`) |
| `components_install` | `poly components install` | `names` (components or presets), `languages`, `paths`, `config`, `dry_run`. Downloads; writes only the component cache. No other action has a dry run: `dry_run` with one is a `usage` error. |
| `components_uninstall` | `poly components uninstall` | `names`. Refuses a component loaded in this process (`isError`). |
| `components_prune` | `poly components prune` | None. Removes cached archives nothing references or used recently. |

The cache actions return `{command, freed_bytes}`, like `poly cache clean|gc --format json`.

There is no `hooks` tool: `poly hooks` is CLI-only.

### Async tasks

Whole-project scopes, and runs or installs that must download a component, return an async
**Task** (SEP-2663) when the client declares the tasks capability: the call returns a task handle and
the client polls `tasks/get`, optionally `tasks/cancel`. The status message names the components;
there is no byte-level progress and no `notifications/progress`, because the core can only answer a
frontend's call, not report during it. A client that does not declare the capability gets a
synchronous, blocking result from the same call, so the tools work either way.

### Components and downloads

In a core build the engines are downloadable components; a bundled build links them in and
nothing is ever missing. `check` and `fix` are **open-world**: a run that needs a missing component
downloads it first, governed by their `install` parameter — `config` (the default, following
`[components] install`), `auto`, or `never` (download nothing and skip the files a missing component
would have handled). A server started with `--offline` never downloads, whatever `install` says.

A run that needed any downloadable component carries a `components` block (`used`,
`installed_now`, `missing`). A missing component that fails the run sets `isError`; one skipped
under `install: "never"` does not, but still appears in `skipped` and `components.missing`.

### Workspace confinement

Every `paths`, `dirs` and `config` argument is canonicalized (symlinks and `..` resolved) and must
lie inside the directory `poly mcp` was started in; otherwise the call fails with an error naming
the path. The `--config` file passed to `poly mcp` is always accepted. Start the server with
`poly mcp --allow-outside-workspace` to lift the restriction.

## Every result identifies the binary that answered

Each result carries a `poly` block (version, build id, channel, executable, pid, `flavor` —
`bundled`, `core` or `partial` — `components_lock` — a digest of the embedded component lock, or
null — and `engines`, a blake3 digest of every engine linked into the binary and the upstream version it wraps) in
`structured_content` and in `_meta`, because an MCP caller has no `poly --version` to fall back on.
The `info` `version` topic returns the full engine→version map the digest summarizes.
The server fingerprints its own executable at startup and re-checks it per request: if the binary is
replaced or deleted underneath a long-lived server, every call but `info {topics: ["version"]}`
fails rather than answering with superseded behaviour.

## Three per-file outcomes, not two

`check` and `fix` results tell three outcomes apart:

- **Checked** — counted in `summary.checked`. A checked file with findings has a `results` entry;
  a checked, clean file has **no** entry at all, so absence from `results` alone proves nothing.
- **Skipped** (`skipped` field) — poly correctly declined the file, for example a template dialect
  no backend handles. Not a failure.
- **Errored** (`error` field) — poly failed to process a file it accepted: unreadable file, backend
  crash, bad engine config. Deliberately distinct from a skip, which is a decision rather than a
  failure.

Each result also carries run-level `errors` and `skipped` arrays and a `summary`:

```json
{
  "results": [...],
  "errors": [],
  "skipped": [{ "path": "main.zig", "reason": "no lint rules for Zig" }],
  "summary": { "checked": 12, "skipped": 1, "errored": 0 },
  "configs": [{ "hash": "1/9f2c4a1b7e3d05f8" }]
}
```

`configs` fingerprints every configuration that governed the run; each result's `config` field
indexes into it (omitted when `0`). An entry also carries `withheld` when the config's exec-capable
keys were withheld by trust (ADR 0059). It is what tells a caller whether two clean reports from
different calls are actually comparable — a `poly.toml`, a `poly.local.toml`, a nested config or an
`extends` base can move underneath an identical-looking request. When discovery left something out —
excluded files and directories, named paths that matched an exclusion (`excluded_explicit`), pruned
directories, unrecognized files — the document also carries a `discovery` object saying so.

A `degraded` array (omitted when empty) lists `{tool, language, reason, files}` for each native tool
that is on by default or switched on and was not found on `PATH`: its files were formatted by the
tree-sitter tier, or linted without it. They are still checked, and `degraded` does not set
`isError`.

`errors` and `skipped` duplicate the corresponding records in `results` on purpose, so a caller can
gate on "did this run actually check what I gave it" without scanning every record.
**`skipped` deliberately does not set `isError`** — a skip is coverage information, not a failure, and
flagging it would make the error signal useless. That is exactly why `summary` matters: a run where
everything was skipped reports no diagnostics and is not an error, so `isError` alone cannot tell it
apart from a clean pass. **Gate on `summary.checked`.**

The counts are not a partition of `results` and cannot be derived from it — a file checked and found
clean produces no record at all, and a file poly has no rules for can be both a skip and a result,
since the cross-cutting backends still run over it.

This is the same document `poly lint --format json` prints, so an agent and a CI script read
coverage the same way.

### When `isError` is set

`isError: true` means the run did not verify what was asked:

- a file poly failed on (non-empty `errors`);
- a blocking missing component;
- skips over `max_skips`;
- a whole-project phase that was asked for and did not run;
- a run that could not start.

A run that could not start, or whose requested phase did not run, returns
`{error: {kind, message}, summary: null}`, where `kind` is one of:

| `kind` | Meaning |
| --- | --- |
| `paths` | A named path does not exist. Over MCP this used to read as a clean pass. |
| `workspace` | A path lies outside the server's directory. |
| `config` | The config or `poly.lock` failed to load. This used to be a JSON-RPC error. |
| `pipeline` | The run failed to plan, for example an unknown `only` engine. |
| `render` | The result could not be serialized. |
| `usage` | Invalid arguments: an unknown key, a wrong value, arguments that do not go together, or a parameter that does not apply to the chosen `scope`, `action` or `topics`. |
| `untrusted` | `scope: workspace` in a repository whose `[hooks]` are not trusted (`poly trust`). |
| `no_workspace_tools` | `scope: workspace` with no whole-project tool configured, or the phase disabled. |

Only an unknown tool name is a JSON-RPC error; everything wrong with a call to a tool that exists is a
result.

Error-severity findings and formatting drift are **not** errors: they are the CLI's exit 1 and
appear in `results`.

<Aside type="danger" title="Check `isError` before trusting the result">
    Before this shape existed, a file poly failed to process was absent from the output entirely —
    indistinguishable from a file that was checked and found clean. An agent that gated on "no
    findings in `results`" was reading a run that had silently failed to check some files as a clean
    pass. Check `isError` (or the `errors` array) **first**, then `summary.checked` to confirm the
    run covered what you gave it; only then read `results` for diagnostics.
</Aside>

## Driving poly from the CLI instead

If you are not going through MCP, the same discipline applies with `--format json` or
`--format toon`:

<Steps>

1. Check, and read the machine-readable report:

   ```sh
   poly lint --format json --workspace never . > findings.json
   ```

2. **Read the exit code, not just the payload.** `0` is clean, `1` means error-severity findings,
   and `2` means the run verified less than it claims. The whole-project phase's own pass/fail is
   written to stderr so stdout stays a single valid document.

3. Fix, then re-check:

   ```sh
   poly lint --fix .
   poly fmt --fix .
   poly lint --format json --workspace never .
   ```

</Steps>

`--format toon` is compact enough to hand to an agent without burning its context window;
`--format json` is there when you want a document to parse with a schema.
